A guided tour of the code

How Teleboxel works

Teleboxel is a minimal, fast WebSocket server for a shared voxel world, written in Rust on Tokio. It owns a sparse, infinite voxel grid and a set of replicated entities. Clients edit the grid and move their entities; the server orders the changes, stores them and forwards them to the nearby clients.

This page explains; it does not specify. The code is the specification, with every design reason as a comment next to the code it explains, and the wire contract for client authors is PROTOCOL.md. Each section below names the code it describes, so you can read the real thing next.

  • 1world task owns all state
  • 30 Hzfixed tick
  • 16³voxels per chunk
  • 32slots in each client's outbound queue
  • ~50clients, by design

What it is, and isn't

README.md · Cargo.toml

The server is the one place where the world is true. Clients send what they want to happen; the server decides the order, applies it and tells everyone who can see it. It is deliberately small: four dependencies (tokio, axum, fastwebsockets, bytes) and four source files.

File What lives there
src/protocol.rs The wire format: decoding client messages, encoding server messages.
src/main.rs HTTP/WebSocket accept and the connection lifecycle.
src/world.rs World state, the tick and per-client sync.
src/bin/bot.rs The load bot.
tools/client.html A 2D debug client, one HTML file.

Just as important is what it leaves out:

  • Auth, anti-cheat, rate limits. Clients are trusted.
  • Persistence: the world lives in memory.
  • Physics and gameplay rules, which belong in the client.
  • More than ~50 concurrent clients.
  • Transports other than WebSocket.

The big picture

src/main.rs · main, ws_handler, handle_client, write_frames — src/world.rs · Command, World::run

Everything runs on one Tokio runtime. There is exactly one task that owns the world, and per client, two small tasks that move bytes between the socket and the world. Connections and the world only talk through channels.

  • One owner, no locks on the world. main moves the World into its own task. Connections never touch it; they send Command::Join, Message and Leave.
  • Validate once, at the edge. The reader decodes every message with protocol::decode_messages; malformed input closes the connection. The world trusts the commands it receives.
  • Two halves, not one select!. fastwebsockets' read_frame is not cancel-safe, so reading and writing are separate halves of the split socket. Pongs and close replies from the reader go through the same write half, shared behind a mutex.
  • The world speaks bytes, not WebSocket. It builds each client's frame as Bytes and assumes an ordered, reliable stream. The writer just copies frames to the socket.

A connection's life

src/main.rs · handle_client, read_hello, read_messages, close_on_error, End — src/world.rs · World::apply

From the upgrade to the last log line, one function, handle_client, runs the story. Read the diagram top to bottom.

Joining

  • read_hello requires HELLO as the whole first message: version 1, view_h ≤ 16, view_v ≤ 8 (MAX_VIEW_H, MAX_VIEW_V: they bound each client's tick cost).
  • The id comes from a global counter, NEXT_ID, and is never reused, not even once exhausted: clients and the world key entities by id. Exhaustion closes with 1011 entity ids exhausted instead of WELCOME.
  • Command::Join hands the world the client's frame queue tx and the disconnect sender. The server prints client 3 connected (view 8/4).

Leaving, with a reason

handle_client waits in a biased select! on two things: the reader finishing, and the disconnected oneshot resolving. The reader goes first, so its reason wins when both are ready. The world's signal is needed because a client that stops reading blocks the writer mid-write, and with it the pongs and the close; only the world can notice (a new frame finds the queue full) and end the connection.

Then it sends Leave, which is a no-op if the world already removed the client, attempts a 1002 close if the input was malformed (raced, again biased, against the world forgetting the client), logs exactly one line and aborts the writer. Dropping both halves closes the socket.

How it ended (End) The one line on stdout
The client closed client 3 disconnected: closed by client
EOF, reset, aborted, broken pipe client 7 disconnected: connection lost (Unexpected EOF)
Malformed input (closed with 1002) client 9 disconnected: protocol error "truncated message"
The world gave up on it client 12 disconnected: outbound queue full

Before its HELLO is accepted a client has no id and is logged as new connection. Leaving, however abruptly, is the client's doing and goes to stdout; stderr is only for failures on the server's side (upgrade failed, close failed, ids exhausted, anything unexpected).

The tick

src/world.rs · World::run, step, apply, send_frames

The world does nothing between ticks. Thirty times a second it runs one step:

  1. Wait for the ticker An interval of 1/30 s. A late tick is skipped, not made up with a burst (MissedTickBehavior::Skip).
  2. Drain the commands Everything queued since the last tick, applied in order. Join sends WELCOME, in its own frame; Leave removes the client; ENTITY_STATE stores the entity and marks it changed; VOXEL_EDITS writes voxels into their chunks, creating a chunk on its first edit, and records the tick's edits per chunk. Commands are only read here: nothing is sent between ticks, so reading them earlier would only add wakeups.
  3. Build one sync frame per client Each entity's ENTITY_STATE is encoded once, for every viewer. Then per client with an entity: u32 tick, then sync_chunks, then sync_entities. No messages, no frame.
  4. Hand it over with try_send Never awaiting a client. A full queue marks the client for disconnection with the reason outbound queue full; a closed one means the connection already ended.
  5. Clear the tick's state Per-chunk edits, changed entities, destroyed entities.
  6. Remove disconnected clients After the clear, so the others get ENTITY_REMOVE next tick. The reason, if any, goes to the connection through its oneshot.
  7. Advance the tick tick.wrapping_add(1): a u32 that wraps after ~4.5 years at 30 Hz.

↻ back to 1

Reliable, or disconnected. The world never drops a frame: when a new frame finds a client's 32-slot queue full (about 1 s of frames at 30 Hz), the client is disconnected instead. So the world only has to remember what each client has, never which version. Dropping frames, as a transport over unreliable datagrams would, needs versioned state per client, and is deferred.

Every 5 s the world prints what the tick cost. Only step is timed, not the wait:

tick avg … max … | out … KiB/s | clients … entities … chunks …

A sparse, infinite world

src/world.rs · Chunk, Client, sync_chunks, sync_entities, in_box

The grid is a HashMap from chunk coordinates to chunks of 16×16×16 voxels, each voxel a u16 block id (0 is air). A chunk exists from its first edit on and is never removed; a chunk that does not exist is all air. Voxel coordinates are i32, so the world is as good as infinite.

  • A voxel's chunk is v >> 4 per axis; its index inside the chunk is x | z << 4 | y << 8 (local coordinates), so each horizontal layer is contiguous.
  • Entity positions are 24.8 fixed point (1/256 voxel), so an entity's chunk is pos >> 12. One entity per client; its id is the client's id.

What each client sees

A client's view is a box of chunks around the chunk C that holds its entity: H chunks each way horizontally, V vertically. What it already has stays until it is beyond H + 1 / V + 1. Without that hysteresis ring, moving back and forth across a border would unload and resend a whole plane of chunks every time.

Chunks: sync_chunks

Its work is bounded by what changed, not by the view size. Each tick it does up to three things:

  1. Rescan, only when C changes Scanning the view every tick is up to 33 × 33 × 17 lookups per client, over the 1 ms tick target at 50 clients. So only when the entity crosses a chunk boundary: known chunks beyond H + 1 / V + 1 get CHUNK_UNLOAD, and every existing chunk in view that the client lacks goes into pending, sorted so the nearest comes out first.
  2. Forward this tick's edits A chunk the client has gets them wherever it is, even in the ring: a known chunk is not sent again just for re-entering the view, so without its edits it would come back stale. See the diagram below.
  3. Fill the view, gently Pending chunks go out as CHUNK, nearest first, at most 8 per tick (MAX_SNAPSHOTS_PER_TICK: 64 KiB per frame, about 2 MiB/s), and only while the client's queue is empty, so a slow link does not fill up with snapshots while entity updates wait behind them.

Entities: sync_entities

Checked every tick, because entities move on their own, with the same box and ring as the chunks. An entity entering the view (H, V) arrives as ENTITY_STATE; a known one is resent whenever it changed; one beyond H + 1 / V + 1, or whose client left, gets ENTITY_REMOVE. A client never receives its own entity, and has no view at all until its first ENTITY_STATE.

The wire, at a glance

src/protocol.rs — the full contract: PROTOCOL.md

Binary WebSocket messages. Integers are little-endian and fixed width, with no padding. Each message starts with a u8 type, and there is no per-message length: the size follows from the contents. So malformed input is an error, never skipped or guessed; the connection is closed with the error as the reason.

A client message: messages, no header.

0x02 ENTITY_STATE …0x03 VOXEL_EDITS ……

A server frame: the tick, then one or more messages; chunks come before entities, the order send_frames builds them in.

u32 tick0x85 CHUNK_EDITS …0x84 CHUNK …0x82 ENTITY_STATE ……

Clients send HELLO, ENTITY_STATE and VOXEL_EDITS; the server sends WELCOME, ENTITY_STATE, ENTITY_REMOVE, CHUNK, CHUNK_EDITS and CHUNK_UNLOAD.

  • The tick lets clients interpolate entities by server time rather than by arrival time, which carries network jitter.
  • Close codes: 1002 with a reason for malformed input (for example truncated message, view_h too large), 1011 when ids run out.
  • Byte layouts, the full lifecycle, every close reason and the limits are in PROTOCOL.md; the tests in src/protocol.rs pin the encoders' exact bytes.

Tools

src/bin/bot.rs · run_bot — tools/client.html

Two clients ship with the server, for two different questions.

The load bot

“How long does a tick take at 50 clients?”

  • N well-behaved clients. Each walks a circle of radius 24 voxels at 6 voxels/s, around grid points 48 apart, so it crosses chunk borders and sees its neighbors.
  • It sends its entity every server tick, edits the voxel under it at the given rate and reads every frame.
  • Every 5 s it prints what the bots received, to cross-check the server's out figure.
  • bot [clients=50] [addr=127.0.0.1:3000] [seconds=30] [view_h=8] [view_v=4] [edits_per_sec=2]

The debug client

“What exactly did the server send me?”

  • One HTML file, opened from disk. A top-down view of one horizontal layer, with the view (H) and hysteresis (H+1) boxes drawn from the position as sent.
  • It draws only what the server sent: its own edits are sent, never applied locally, and appear when their echo arrives.
  • WASD moves, Q/E changes the layer, drag paints, right drag erases, the wheel zooms (2–32 px per voxel), 1–9 or the palette pick a color.
  • Edits go out as one VOXEL_EDITS per tick, and its entity only when it changed. 
cargo run --release                                     # server on :3000, stats every 5 s
cargo run --release --bin bot -- 50 127.0.0.1:3000 60   # 50 bots for 60 s

Measured, and deferred

README.md · Measured, Deferred

With 50 bots on the same machine as the server (i7-13700H, Windows 11, loopback), a tick takes 0.5–0.8 ms of work on average, within the 1 ms target. The worst ticks, 2–4 ms steady and ~10 ms while all 50 clients join, are accepted: the tick period is 33 ms.

Optimizations

Measure first; chunk traffic dominates.

  • compact chunk encodings (uniform, RLE, palette)
  • snapshot encodings shared between clients
  • zero-allocation frame building

Features

  • drop-tolerant sync (versioned state), for UDP/WebTransport
  • PING/PONG for client RTT
  • several entities per client
  • prediction and reconciliation
  • validation, rate limits, auth
  • persistence
